# ZImage 电商生图方案与当前项目：挑剔者审查

日期：2026-09-07（America/Los_Angeles，UTC 为 2026-09-08）。审查基线：`bc05783d49645976cbfc54882c4ec8f7ae078e28`。结论依据本地代码、全部相关迁移覆写与研究文档；不代表线上故障已经发生。

## 审查结论

“新增 Senyu 式入口、共用工作台、复用现有模型并接入精选模板”的方向可以保留。当前不宜直接按 v0.1 全量开发：既有执行链存在会错误创建任务、丢失消费记录或无法恢复结果的缺陷；方案还缺少可靠的逐图选择规则，并把首版扩大到了独立排版系统。

本轮确认 **6 项当前代码问题、3 项方案缺口**。产品决策已逐题收敛，PRD/技术方案更新为 v0.2；**没有修复业务代码，没有改变数据库、部署或线上账号**。工程细节无需继续让用户逐项决定。

P1 表示应优先修复、会影响首版关键正确性；P2 表示仍须处理的可靠性或流程缺口。这些优先级不表示已经测得线上发生频率。

## 一、当前代码问题（均未修复）

### C01 · P1：工具开启被直接当成生图授权

- **证据**：[UnifiedWorkspace.tsx](../../../apps/web/features/workspace/UnifiedWorkspace.tsx)，286–289、558–572 行。`submit` 仅根据 `imageCreationEnabled` 调用 `beginImageTurn`；Skill 可以开启该能力。聊天分支 484–493 行固定传 `imageToolEnabled:false`，并未承担规划与确认。
- **触发**：选择白底 Skill 后发送“先分析构图，不生成图片”，或没有参考图/商品描述便发送“先聊聊”。
- **后果**：非生成意图也进入图片提交；关键资料缺失不会按旧正式需求 P2-US2-AC11 先追问，新方案 EC-07 同样无法满足。
- **处理**：将能力可用与用户确认分开。按 D08，三个旧 Skill 与向导都先生成方案，带明确版本与 slot 的确认才入队；普通讨论、补资料不入队。销售场景按 D11 校验真实商品图。
- **验收**：上述两个负例均无图片请求/额度变化；明确确认只生成选中项；旧 Skill 链接与历史仍可使用。同步正式需求和旧测试，不能只新增入口页面。

### C02 · P1：删除会话会连带删除已消费额度记录

- **证据**：[foundation.sql](../../../supabase/migrations/20260824061043_phase1_foundation.sql)，130–141 行，quota_ledger 的 batch/generation 外键级联删除；[cleanup.sql](../../../supabase/migrations/20260824074500_phase1_cleanup.sql)，86 行物理删会话；[generation_queue.sql](../../../supabase/migrations/20260824063746_phase1_generation_queue.sql)，125–133 行以现存 reserve/release 账本计算每日 30 张上限。未发现后续迁移改变这些外键与计量逻辑。
- **触发**：当天成功生成后删除对应会话，等待清理完成，再次提交。
- **后果**：已发生消耗的账本随会话删除，日额度计算减少，限制可被绕过；新增执行组沿用配额锁也解决不了数据已被删的问题。
- **处理**：将消费事实与会话/作品生命周期分开。业务引用可失效，但已消费额度不能因删除内容返还；保留独立幂等业务标识，并调整现有非空引用约束。
- **验收**：成功生成→删除会话→完成清理→查询/提交，已消费额度保持；确实未派发的取消才按规则释放。

### C03 · P1：清理与在途生成竞争，可能留下无数据库记录的图片

- **证据**：[cleanup.sql](../../../supabase/migrations/20260824074500_phase1_cleanup.sql)，39–55 行只收集当时已登记的 storage_path；[generation-worker](../../../supabase/functions/generation-worker/index.ts)，271–287 行在 Provider 返回后上传再落库；[cleanup-worker](../../../supabase/functions/cleanup-worker/index.ts)，74–84 行删快照对象后完成业务删除；[auth_accounts.sql](../../../supabase/migrations/20260906173500_phase2_auth_accounts.sql)，137–140 行将账号在途任务标为 failed，未取消正在运行的 Worker。
- **触发**：Provider 调用尚未返回时删除会话/注销；清理取得对象快照后，旧 Worker 才上传图片。
- **后果**：快照遗漏新对象，业务行已被删除或不再 processing，完成 RPC 拒绝落库。图片没有资产行与到期记录，常规清理无法再定位；注销时标记 failed 本身也不能阻止旧 Worker 写入。
- **处理**：删除先阻止新领取，协调在途执行；上传路径提前登记，完成前检查所有者/任务状态；落库被拒绝时安排持久化补偿清理，并覆盖无主对象巡检。
- **验收**：受控暂停 Provider 返回，穿插会话删除/账号注销后继续执行，最终没有可访问资产或遗漏对象；测试须覆盖竞争顺序，不能仅测静态删除。

### C04 · P2：固定 120 秒可见性可能终结仍在正常运行的任务

- **证据**：最新 [emergency_stop.sql](../../../supabase/migrations/20260824231500_phase1_generation_emergency_stop.sql)，19 行领取可见性 120 秒，47–53 行已提交 processing 重领返回 fail_unknown；[generation-worker](../../../supabase/functions/generation-worker/index.ts)，149–183 行参考下载与仅覆盖 Provider 调用的 90 秒超时，309–319 行将 fail_unknown 写为终态。未见续租机制。
- **触发**：下载、Provider 调用、上传与落库总耗时超过 120 秒，第二个 Worker 再次领取。
- **后果**：任务被标为失败并归档，原 Worker 随后取得图片也会因不再 processing 而无法完成；正常在途与失联执行未区分。
- **处理**：增加有界总执行时间、续租、领取版本校验与到期核对。租约过期不是可直接认定失败的证据，也不能盲目重发模型调用。
- **验收**：受控延迟超过原租约后仍只执行一次，合法执行可完成；崩溃执行能够核对和接管。

### C05 · P2：上传成功后落库失败，已有结果没有独立恢复路径

- **证据**：[generation-worker](../../../supabase/functions/generation-worker/index.ts)，271–287 行将上传与完成 RPC 合并 catch，统一记录 result_storage_failed，未持久保存本次已知对象路径；[generation_queue.sql](../../../supabase/migrations/20260824063746_phase1_generation_queue.sql)，311–317 行失败重做只筛 status=failed，578–592 行完成仅接受 processing。
- **触发**：Storage 上传成功，但完成 RPC 在提交前暂时失败。
- **后果**：已有图片不能通过任务记录恢复，原预占不释放；用户“失败重做”会创建新生成并再次消费。未知提交也进入普通 failed 集合，没有单独的核对入口。这是再次执行的成本，不是同一账本重复插入。
- **处理**：持久记录 Provider 完成、对象上传、完成落库三个阶段；完成操作幂等补写，失败重做排除待核对/待落库项。Provider 不提供查询能力时明确标记不可自动恢复，不能伪造核对结果。
- **验收**：注入上传后 RPC 失败与响应丢失，恢复不新增模型调用；不丢已知对象；未知结果不会被批量失败重做静默重发。

### C06 · P2：账号清理任务领取后崩溃无法重新领取

- **证据**：[auth_accounts.sql](../../../supabase/migrations/20260906173500_phase2_auth_accounts.sql)，149–153 行只领取 pending/failed 并设为 processing；无过期 processing 重领。普通 [cleanup.sql](../../../supabase/migrations/20260824074500_phase1_cleanup.sql)，23–25 行已有五分钟过期重领，但账号清理没有同样处理。
- **触发**：领取成功后 Worker 被终止，或错误状态回写也失败。
- **后果**：任务永久留在 processing，账号长期 deleting，后续清理不会再选到它。
- **处理**：账号清理增加租约、领取版本与超时重领，删除和完成均可幂等重试；处理重试次数耗尽后的可观测人工处置。
- **验收**：领取后终止执行，租约到期后可重新领取并最终完成；旧领取者不能覆盖新执行状态。

## 二、方案缺口与本轮处理

### D-A · P1：跨版本单图重做缺少当前交付选择

v0.1 技术方案第 5–6、8 节只定义 run/item 和原结果保留，没有定义“第三张重做后，整套下载用哪五张”。只读当前 revision 会丢其余四张，简单取最近成功结果又会覆盖用户切回的旧图。

**用户 D10 已决定默认采用新图，旧图可切回。** v0.2 补充持久化 CreativeSelection、未影响 slot 继承、兼容性标记、迟到结果保护和固定导出清单。工程仍须实现与测试；更新文档不算关闭代码风险。

### D-B · P1：精确文字与独立改字承诺超出当前生图范围

v0.1 编译器把“准确文字”写入 prompt，第 11 节却又承诺确定性合成与改字不生图。如果旧文字已画进底图，叠加文字不能清除它，也不能保证商品不被遮挡。该方案还新增 Node 合成执行器、文本布局、字体与合成资产生命周期，已超出简单 Senyu 式生图入口。

**用户 D09 已选择 AI 整图，改字重新生成。** v0.2 移除首版独立文本层与长图合成，将详情先交付为独立图片集合；不承诺 100% 准确文字。原 19–30 人日估算撤回，待结合旧流程迁移和底座修复重新拆分。Senyu 的生成效果未经本轮付费实测，不应将其前台能力描述当成现有模型效果证明。

### D-C · P2：样图转为后续参考缺少真实引用路径

v0.1 PRD 7.2 允许采用首张样图，但技术只接受 reference_uploads.id，而生成图片是 generationId。没有转换路径就可能只有 prompt 提到“参考样图”，模型却没有收到它。

v0.2 明确受保护的生成结果转上传引用、来源关联、同账号同会话有效性、对象失败清理与合计四张限制；满额时先明确替换素材。这是已有产品规则下的工程补全，无需新建跨会话资产库或增加用户决策。
