# 资源不足时的最小安全切换建议

2026-10-29 UTC。仅基于既有证据和本轮必要源码/离线核验；没有实现新兼容层、启动服务、访问生产、购买扩容、修改配置或重试被拒动作。**推荐当前保持 B0；取得缺失输入后，优先评估单实例顺序维护。不要为赶上线另造未验的 Flight 架构。** 本文不是上线许可，当前仍未通过完整验收。

## 草稿与旧进程是两件事

旧草稿在浏览器内存中，不在服务端 B0 的堆里。保留它需要原 JS/组件树继续运行、旧协议与资源匹配、同一真实 owner 连续，避免完整 document 导航、卸载或认证错误重建；**不意味着完整旧服务必须永久运行**。本地已证明：切后真实收到原 B0 Flight 时，无会话文本保留；已有会话另有缓存返场控制。引用和真实 focus 重检仍被锁屏阻塞，不扩大该结论。[补验范围](./cutover-compatibility-validation-20261029.md)

但原 B0 已准入的 SSE graph、RPC、Sharp/Storage、续租和补偿可能仍由该 PID 持有。新 API、静态文件、另一个同版进程都不能接管任意在内存中的 Promise/native 执行，账务或队列状态也不覆盖所有最终收尾。**在原 PID 工作闭合前仍须保留原进程；轻量层不能把这部分 RAM 先从预算中删掉。** 部分已持久入队的工作由既有 Worker 负责，可按原ID移交；它不证明其他旧进程工作结束。独立 first-window/恢复执行器已本地实现复审通过，当前缺的是原 B0 completion 事实及真实部署验证，不是再写一套执行器。

顺序维护只是**取得完成证据之后**的最简目标，不保证原材料一定能补齐。若原记录根本不存在，当前就没有已证明“不丢业务”的首次停机路径；增加容量可保留原进程并延后退出，但不会自动补回历史凭据。

## 轻量兼容层能做到哪里

只读静态层可低成本保留原 B0 chunks、明确已静态化的公开协议输出；旧 JS 的新业务请求也可以由 B1 按旧客户端合同处理。**B1 必须继续报告真实 B1 身份**，维护真实 Cookie/owner、请求ID、SSE与未知结果语义，不能将 B1 Flight 的 `b` 或导航部署 header 改成 B0 来骗过旧客户端。

当前不能把这一方向当作完整、无需旧 renderer 的切换方案，依据如下：

- 同一 `/home` 已有 tree预取284B、segment18071B、导航18895B等不同原响应；路由树、Next-Url、预取类型和查询会影响协议。Next16.4.1与实际旧JS的**导航fetch**在内容类型/状态或构建身份不匹配时走整页导航；prefetch/segment cache也可能先拒绝缓存，并非每次预取失败立即换document。只按pathname回一个抓包文件不成立；按原构建静态manifest语义归并变体则有可能，但尚未验真。
- 真实 B0 并非全部空壳页面：`app/page.tsx:5` 使用 `connection()`；`create/[scene]/page.tsx:4-7` 处理参数/不存在场景；HTTP业务模式下 `account/page.tsx:14-24` 按当前Cookie读取账号、处理401重定向并把真实账号传入组件。会话原Flight还含具体UUID。通用公共缓存不能替代这些动态/身份上下文，更不能共享他人的私有payload。
- B0 standalone打包未专门排除 `.rsc/.meta/.segments`，Next也支持相应静态输出；**不能断言原制品没有可复用文件**。但现有435文件库存是 `.next/static`，尚无目标9c `server/app`/prerender清单及完整原响应映射；动态页面也不能因找到部分 `.rsc` 就视为覆盖。5条Flight和一张公共optimizer仅证明有限回放。
- `/_next/image` 不必永远依赖旧进程：可研究由 B1 用原资源/验证规则承接。但须验证真实授权、URL/Accept/尺寸/格式、缓存未命中和native峰值；现有一次B0 cache HIT不足以证明全部行为。

若为动态账号、参数化Flight和旧client reference manifest嵌入旧Next renderer，或另起只读旧renderer，就引入多构建运行时/新认证边界。它可能比执行全部旧业务更省内存，**也可能仍加载旧依赖和缓存；没有实测，不能算零重复内存或称为简单静态层**。本轮不实施它，也不以此绕开资源门槛。即便它未来验证成功，仍须先解决原PID任务闭合。

离线来源绑定、实际旧JS校验及反例在 `.design-qa/2026-10-29-separation/minimal-cutover-analysis/`，没有通过重写原抓包进行证明。

## 最小方案比较

| 方案 | 旧页/任务与资源代价 | 当前判断 |
| --- | --- | --- |
| 保持B0，完成输入和正式制品 | 原页/原进程继续；不增加实例 | **现在执行的推荐状态**，迁移延后，不等于完成上线 |
| 低峰单实例顺序维护 | 用户确认保存并离开旧页；原PID全部收尾后旧停→native验证→B1启动；无双服务常驻预算 | **优先的最终拓扑**，仍缺旧页/原工作闭合；低峰、等300秒或stop30秒都不补证。门槛未知即取消窗口、保留原进程 |
| 精确B0旧协议 + F1/B1临时并行 | 可让旧页继续，需真实同owner连续；原PID在收尾前仍占RAM，未来旧renderer退休另有条件 | 同机双850MiB预算1700大于实测1608.910MiB，当前不放行。可在已存在且获授权的匹配容量上另审；更小配置也要实测，不能仅压限额 |
| 静态/多构建“轻量兼容层” | 静态公开部分可行；完整动态/认证/图片仍需实现和验证，不解除原PID责任 | **不作为本次赶期方案**，没有证明其完整性或内存优势，不新增该架构 |

## 低峰与临时容量的成本、风险边界

低峰减少受影响人数，不降低安全条件，也不消除休眠旧页。维护前须确认受影响范围、草稿/引用保存退出、原操作最终凭据和精确恢复目标；不能先让旧页收到认证503而把它称为迁移通知。窗口要有“仍未知则取消”的预算，不能把超时当可杀进程的许可。

临时扩容/另机只解决容量，不解决历史收尾和旧页退出。当前B0 cgroup约388MiB、单PID RSS高水位344MiB，均非完整峰值；正式Linux B1/native并发峰值、部署盘量峰值未知。[原始资源数字](./coexist-resource-plan-20261029.md) 只能否定当前双850预算，不能证明所有较小配置永远不可行。若规格变更需要停机，它本身也先受B0安全退出门槛约束，不能假设支持无停机扩容。

本轮未读取账单或报价，没有金额估算。任何临时付费方案须先只读核实实际规格/可用容量、是否停机、计费粒度、恢复原规格条件及报价，再由用户决定**规格/金额上限、最长持续时间、复核与取消时点**；不能只算几小时RAM而漏掉仍须保留的B0、恢复副本、暂存、日志/流量和计费尾部。复核到期不等于允许强制缩容。当前不购买、不扩容，也没有可直接批准启动的资源执行单。

## 下一步与用户需决定的范围

1. 先等待已有输入：解锁Mac补引用/真实focus；当前私有分支源码发布授权；Nginx `/tmp`上传测试授权。未回复前不重试，旧dirty源码包保持原状，正式Linux输入仍须真实clean提交与完整源清单。
2. 正式Linux制品可达后，补匹配目标的native/允许并发/内存与新增磁盘峰值、真实身份/API/图片/回退证据；原B0只读事实另按同PID核验，不能从新B1计数推断它已空闲。
3. 用户需要选择：能否组织旧页保存并离开、接受哪个**可取消**的低峰维护窗口；若必须保留旧页继续运行，是否提供一处已存在且已授权的匹配资源，或仅批准进一步核价一个有明确上限的临时容量候选。不是现在授权购买、启用或接受丢稿。
4. 无论选哪条，原进程completion证据缺失时仍不能安全stop；需由已有合法操作者/原操作记录提供事实。不能重发计费请求“验证”，也不能用清队列、删intent或等待代替。
