# 登录验证与 MiniMax 聊天修复验收

## 范围与根因

在当前已有未提交变更的工作区实施，仅覆盖桌面 Web。未修改模型配置、公共 API、数据库迁移、Worker 或部署。

- 真实 MiniMax 流返回 HTTP 200、`text/event-stream`，第 14 帧给出 `finish_reason: stop`，共 15 个数据帧后 EOF，无 `[DONE]`。旧解析器只接受 `[DONE]`，导致已有完整文本仍进入失败分支。
- 服务端先保存用户消息；流失败时不会保存错误行。旧前端去重又要求匹配错误行或已保存助手 ID，因此本地用户消息与服务端用户消息同时显示。
- 登录页验证码使用自动主题，在当前深色系统偏好下呈现黑色块；成功回调未更新提示文案。

## 修改

- 验证组件使用 `light` / `flexible`，外围采用共享颜色变量和独立 CSS Module；加载、待验证、成功、过期、组件失败、脚本失败分别显示对应文案。重新验证保留表单输入并忽略旧组件回调。没有改动或裁切 Cloudflare iframe。
- 流解析接受明确的 `stop` 或 `[DONE]`，处理分片和 EOF 尾帧；缺少结束信号、长度截断、内容审核、异常工具结束和上游错误仍按对应失败处理。
- 模型调用、统计、保存拆分。统计失败不会阻止完成；保存失败保留本地回复并提示保存失败，不提供会重新调用模型的重试按钮。
- 路由、HTTP gateway、工作区均锁定首次终态，成功后的连接清理异常不会追加失败。Mock 图片工具的排队事件也改为在完成事件之前发出，保持共同终态语义。
- 去重可独立匹配本轮唯一新增的服务端用户消息；保留稳定映射并支持错误迟到。历史同文、并发同文和归属不明确的尝试不做全局文本去重。
- 诊断日志仅记录阶段、关联标识和受控错误码，不记录消息正文、密钥或任意异常详情。

## 真实环境证据

在现有 Chrome 登录态、`http://localhost:3000/`、当前 MiniMax 配置下创建单独验收会话：

1. 短消息让模型记住“蓝色纸船”，成功回复“已记住蓝色纸船”。
2. 多轮追问暗号，成功回复“蓝色纸船”，确认历史上下文传递。
3. 请求约 1000 字、四段故事，完整显示四个小标题，结束语“蓝色纸船的旅行结束了。”可见。
4. 刷新页面后三条用户消息及三条助手回复均保留；每条问题只出现一次，无服务不可用或流中断提示，输入框为空。
5. 开发日志对应三次出现上游完成、回复保存、终态发送记录，无本轮聊天失败记录。

另有一次直接上游短消息调用用于确认结束帧格式；真实调用合计四次。UI 验收使用原有登录态，没有重新登录、注册或提交邮件；图片额度显示始终为 25 张，没有图片生成。

登录页实际 Cloudflare iframe 已目视确认浅色、宽度对齐、成功文案正确；切换注册和找回密码后均重新建立验证并显示成功状态，未提交表单。当前环境使用 Cloudflare 官方测试 site key；这项证据覆盖外观与客户端状态，不等同于生产反机器人验证验收。
